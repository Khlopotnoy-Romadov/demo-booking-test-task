# Бронирование переговорных

## Запуск

Нужны Docker и Docker Compose.

```sh
docker compose up -d --wait
docker compose exec app php artisan migrate:fresh --seed
```

Первый запуск занимает несколько минут: контейнер устанавливает зависимости.

- Демо-страница: `http://localhost:8000/`
- Справочник по API: `http://localhost:8000/api`
- Эндпоинты API: `http://localhost:8000/api/bookings` и остальные из таблицы ниже

## Демо-страница

По адресу `http://localhost:8000/` открывается страница для ручной проверки API. Она нужна, чтобы посмотреть на поведение сервиса без curl и Postman: видно, какие запросы уходят, какие коды и тела ответов возвращаются.

Страница не требует сборки фронтенда: это один Blade-шаблон с inline CSS и обычным JavaScript, `Node.js` и `npm run build` не нужны.

Что на ней есть:

- **Токен** — поле ввода и кнопки «Анна» / «Борис». Выбранный токен сохраняется в `localStorage`, поэтому после перезагрузки остаётся прежним. Смена токена сразу перезагружает список броней и расписание.
- **Переговорные** — список комнат с офисом, вместимостью и часовым поясом. Данные приходят из базы при рендере страницы.
- **Новая бронь** — комната, название, дата, начало и конец. Под формой показано, какой именно ISO 8601 уйдёт на сервер, — смещение подставляется от пояса офиса выбранной комнаты. Поля времени принимают любую минуту, а не только кратную 15: иначе браузер блокировал бы отправку и правило про шаг нельзя было бы проверить через сервер.
- **Мои брони** — таблица броней текущего пользователя с кнопкой «Отменить».
- **Брони комнаты на сегодня** — вызов `GET /api/rooms/{room}/bookings/today`.
- **Журнал запросов** — метод, путь, статус и тело каждого ответа. Это основное: здесь видны `201`, `422` с расшифровкой `errors`, `403` при попытке отменить чужую бронь и `204`.
- **Правила бронирования** — краткая памятка прямо на странице.

### Как проверить на ней правила

1. Создайте бронь на 10:00–11:00 в комнате «Арбат». В журнале будет `201`.
2. Отправьте `10:00–11:00` ещё раз — `422`, в теле `errors.starts_at` про занятое время.
3. Создайте `11:00–12:00` в той же комнате — `201`. Так видно, что встречи «впритык» не конфликтуют.
4. Попробуйте `10:07–10:52` — `422` про шаг 15 минут. `10:00–14:15` — `422` про максимальную длительность.
5. Выберите комнату из Новосибирска — в подписи под формой смещение станет `+07:00` вместо `+03:00`. Возьмите `19:00–20:00` — `201`, ровно до закрытия. Затем `19:30–20:30` — `422` про рабочее время: конец выходит за `20:00` по поясу офиса.
6. Нажмите «Борис» и попробуйте отменить бронь Анны — `403`.
7. Вернитесь на «Анну», отмените бронь — `204`, строка исчезает из таблицы.

Демо-токены постоянные и хранятся в базе как хеши, это сделано только для удобства демонстрации. В реальном приложении токены выдаются через Sanctum и не лежат в репозитории.

### Если страница пустая

- **Нет комнат в списке** — не выполнен сидер: `docker compose exec app php artisan migrate:fresh --seed`.
- **`401` в журнале** — токен не совпадает с сидером; нажмите «Анна» или «Борис».
- **Ошибка CORS** — страница и API на одном домене `localhost:8000`, но если вы открыли файл через `file://`, запросы не пройдут: нужен адрес `http://localhost:8000/`.

## API

Все методы требуют заголовок `Authorization: Bearer <токен>`. Заголовок `Accept: application/json` не обязателен: для путей `/api/*` ошибки рендерятся в JSON принудительно.

| Метод | Адрес | Что делает |
| --- | --- | --- |
| GET | `/api` | Справочник: список эндпоинтов и формат авторизации |
| GET | `/api/bookings` | Мои брони |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{booking}` | Отменить бронь |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

Пример:

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "title": "Планёрка", "starts_at": "2026-11-02T10:00:00+03:00", "ends_at": "2026-11-02T11:00:00+03:00"}'
```

### Ответы

| Ситуация | Статус | Тело |
| --- | --- | --- |
| Бронь создана | `201` | созданная бронь |
| Нарушено любое правило бронирования | `422` | `{"message": ..., "errors": {...}}` |
| Бронь отменена | `204` | — |
| Отмена чужой брони | `403` | `{"message": ...}` |
| Брони нет | `404` | `{"message": ...}` |
| Нет или неверен токен | `401` | `{"message": ...}` |

### Правила бронирования

- Брони одной комнаты не пересекаются. Интервалы полуоткрытые, поэтому встречи «впритык» разрешены: `10:00–11:00` и `11:00–12:00` не конфликтуют.
- Длительность от 15 минут до 4 часов.
- Начало и конец кратны 15 минутам.
- Бронь целиком укладывается в рабочее время `09:00–20:00` по часовому поясу офиса, которому принадлежит комната (Москва — `Europe/Moscow`, Новосибирск — `Asia/Novosibirsk`).
- Время принимается в ISO 8601 с любым смещением; хранится и сравнивается как момент времени в `timestamptz`, нормализованный к UTC.
- Автор брони — всегда владелец токена; `user_id` из тела запроса игнорируется.
- Отменить бронь может только автор.
- Ограничений на даты нет: прошедшие и далёкие будущие даты допустимы.

### Гонка при одновременных запросах

Проверка пересечения и вставка выполняются в одной транзакции под `pg_advisory_xact_lock` по `room_id`: второй запрос на тот же слот ждёт завершения первого и получает `422`. Это закрывает гонку при любом количестве инстансов приложения.

Альтернатива, которая дополнительно защищала бы данные от ошибок в любом будущем коде записи, — exclusion constraint на уровне PostgreSQL:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings
  ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (
    room_id WITH =,
    tstzrange(starts_at, ends_at, '[)') WITH &&
  );
```

Он опирается на `timestamptz` в колонках и полуоткрытый диапазон `'[)'`, что даёт ровно нужную семантику. Нарушение даёт SQLSTATE `23P01`, его нужно перехватывать и превращать в `422`.

Лог созданных броней пишется в `storage/logs/bookings.log`.
